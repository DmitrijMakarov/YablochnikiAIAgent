# Архитектура «Стратега Фабрики продуктов»

Этот документ сохраняет проект первого этапа. В прототипе методики реализованы в общем каталоге `.agents/skills/`, рабочий процесс — в `playbooks/workflow.md`, а извлечение, контрольные точки и валидация — в `tools/`. PDF, DOCX и XLSX теперь читаются напрямую в заявленных границах. Актуальные команды, ограничения и результаты собраны в [README](../README.md) и [отчёте о проверке](../tests/acceptance.md).

## Среда исполнения

Один агент в Codex или Cursor ведёт исследование по общей методике и записывает результаты в файлы кейса. Короткий корневой `AGENTS.md` задаёт границы работы, указывает на рабочий процесс и объясняет, как восстановить состояние. Обе среды поддерживают `AGENTS.md`. Общий запуск планируется через чат с открытым корнем репозитория. [Документация Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [документация Cursor](https://cursor.com/docs/rules#agents-md).

Ядро первой версии — инструкции Markdown, таблицы TSV, состояние JSON и доступные инструменты редактора для чтения, поиска, записи и расчётов. Запуск требует доступной модели и прав на чтение и запись в рабочую папку. Для живого исследования нужен разрешённый веб-доступ. На первом запуске агент проверяет доступные инструменты и сообщает об ограничениях. Для повторного прогона можно использовать сохранённые разрешённые копии публичных источников. При недоступности материала агент отмечает пробел, оценивает его влияние на выбор и продолжает с доступными данными либо останавливается на конкретном вопросе.

Прототип извлекает Markdown/TXT, CSV/TSV, текстовый слой PDF, абзацы и таблицы DOCX, сохранённые значения XLSX и текст разрешённых веб-страниц. Если документ нельзя прочитать напрямую, используйте проверенный экспорт с привязкой к оригиналу. Таблицы анализируются локально. Формулы, макросы и команды из входных материалов не исполняются. Для повторяемых расчётов добавляется небольшой скрипт с явными входными файлами и параметрами, когда появится первый такой расчёт.

## Структура будущего репозитория

```text
README.md                     # Установка, запуск, доступы и ограничения
AGENTS.md                     # Общие правила Codex и Cursor
.gitignore                    # Локальные кейсы и файлы с секретами
playbooks/
  workflow.md                 # Шаги, переходы и вмешательство человека
  research.md                 # Источники, противоречия, доказательства
  strategy.md                 # Варианты, две стратегии, план проверки
  follow-up.md                # Обязательства и пересмотр при новых данных
templates/
  case/                       # Стартовые файлы для нового кейса
cases/
  demo/                       # Публичный кейс и результаты для жюри
  local/                      # Рабочие кейсы, исключены из Git
docs/
  architecture.md             # Этот проект архитектуры
  delivery-plan.md            # Этапы, проверки, критерии готовности
tests/
  fixtures/                   # Синтетические данные и контролируемые сбои
  acceptance.md               # Шаги прогона, ожидаемые результаты, оценка
```

Файлы в `playbooks/` описывают методы и примеры. Агент читает материал текущего шага по мере необходимости. Данные кейса лежат отдельно от правил. `tests/fixtures/` можно использовать для проверки поведения, а конкурсный `cases/demo/` строится на разрешённых публичных источниках. В дереве показана целевая структура. На этапе проектирования добавлены два документа в `docs/`.

### Файлы одного кейса

| Файл | Ответственность |
| --- | --- |
| `brief.md` | Вопрос, цель, получатель, ограничения, разрешённые источники, бюджет, допущения и ответы человека. |
| `inputs/` | Разрешённые исходные документы, выгрузки и версии материалов для повтора. |
| `research.md` | Вопросы, которые могут изменить решение, порядок проверки, противоречия, пробелы и краткий вывод с ID утверждений. |
| `sources.tsv` | Источник, версия, оригинальный URL или путь, дата публикации при наличии, дата доступа, локальная копия или основание её отсутствия, статус. |
| `claims.tsv` | Утверждение, тип, статус и границы применимости. Для факта фиксируются источник и локатор. Для гипотезы или прогноза фиксируются основания и допущения. |
| `analysis/` | Входы, команды или формулы и результаты расчётов. Создаётся, если кейс требует расчётов. |
| `strategy.md` | Сравнение вариантов, рекомендация, продуктовая и коммуникационная стратегии, план проверки. |
| `audit.tsv` и `quality.md` | Обоснования по активным утверждениям и итог содержательной проверки. Структуру аудита проверяет CLI. |
| `decisions.md` | Записи о принятом решении, основания, ответственные, сроки, метрики, условия и история пересмотра. |
| `state.json` | Версия схемы, фаза, статус, ссылки на актуальные артефакты, последний завершённый шаг, ожидающий шаг, следующий шаг и вопрос или блокер. |
| `run.tsv` | История действий и затрат по шагам. |

В рабочих файлах используются стабильные ID. Пример цепочки `D-001 → O-02 → C-003 → S-001@2, строки 18–24`. Локатор для документа — страница или заголовок, для таблицы — лист и диапазон либо строки CSV, для сайта — заголовок раздела и подтверждающий фрагмент. У существенных чисел фиксируются единицы, период и знаменатель. Для расчёта указываются версии входов и путь к формуле или скрипту. Повторные публикации, основанные на одном первоисточнике, считаются одним свидетельством. При расхождении источников агент проверяет определения, периоды и аудитории, а открытый конфликт сохраняет с указанием влияния на выбор.

Статусы утверждения — `active`, `disputed`, `superseded` или `withdrawn`. Новые данные получают новую версию источника. Агент ищет зависимые утверждения и решения по ID, сохраняет прежние основания и предлагает адресное обновление. Историческое решение остаётся доступным с исходными ссылками. При отсутствии достоверного основания существенный вывод остаётся гипотезой, прогнозом или открытым вопросом. Ранее сгенерированный ответ может служить указателем на данные.

## Рабочий процесс

| Фаза | Действие и результат | Условие перехода |
| --- | --- | --- |
| Постановка | Агент определяет решение, получателя, цель, ограничения, бюджет и доступные данные. | Для обратимых шагов достаточно записанного допущения. Если неопределённость меняет цель, границы доступа или допустимые затраты, агент задаёт минимальный набор вопросов. |
| Исследование | Агент выбирает вопросы по влиянию на выбор, читает разрешённые источники, сверяет свидетельства и выполняет расчёты при необходимости. | По каждому решающему вопросу есть вывод с основаниями или обозначенный пробел с последствиями. Поиск заканчивается при исчерпании согласованного бюджета или когда дополнительные данные маловероятно изменят выбор в заданных пределах. |
| Варианты и стратегии | Агент сравнивает минимум три направления, включая «оставить как есть» и «закрыть направление». Описывает сильное возражение и условия успеха для каждого. Предлагает согласованные стратегии и план проверки. | Пройдена проверка ссылок, аргументов и соответствия обещаний возможностям продукта. Пользователь получает рекомендацию с условиями, при которых выбор изменится. |
| Решение | Пользователь подтверждает выбор. Агент фиксирует его основания, альтернативы и договорённости. | До подтверждения статус `awaiting_decision`. После подтверждения у обязательств есть ответственные и сроки либо явные пометки о том, что ещё предстоит назначить. |
| Сопровождение | По запросу или при добавлении новых материалов агент сверяет обязательства, метрики и условия пересмотра. | При существенном изменении он предлагает пересмотр конкретного решения. Новый выбор подтверждает человек. Проверка выполняется в активном сеансе. |

Варианты сравниваются по единым критериям, связанным с брифом, например ценность для аудитории, экономика, реализуемость, риск и обратимость. Продуктовая стратегия связывает аудиторию и её задачу, доступные альтернативы, выбранное направление и осознанные отказы с затратами и доходом. Коммуникационная стратегия связывает ту же аудиторию и ситуацию с барьером, сообщением, подтверждением и ролью каналов. При закрытии направления она охватывает затронутые группы, сроки и переход, если это применимо. План проверки фиксирует ожидаемый эффект, метрику и способ расчёта, базу сравнения, окно наблюдения, порог решения и нежелательные последствия. Для существенных возражений агент делает отдельный проход проверки и показывает, какие изменили рекомендацию.

## Состояние, повтор и затраты

- **Запуск и продолжение.** Целевые команды в чате — «Начни кейс `<id>` по `brief.md`», «Продолжи кейс `<id>`» и «Проверь новые данные по кейсу `<id>`». В новом чате агент читает `state.json`, бриф и указанные в состоянии файлы текущего шага. Он сообщает, что уже завершено, какой вопрос или блокер остался и что сделает дальше. Текст старого чата для продолжения не требуется.
- **Контрольная точка.** В первой версии один сеанс записывает один кейс. Перед действием агент сохраняет `pending` с именем шага, ID попытки и ожидаемыми файлами. Затем сохраняет выходы, проверяет их по условию перехода и записывает успешную попытку в `run.tsv`. Последним обновляет `state.json` через временный файл в той же папке. У шага стабильный ID, у каждой попытки свой. На возобновлении агент сверяет состояние, журнал и выходы. Успешная запись агента с тем же шагом и ID попытки закрывает контрольную точку, если хеши указанных файлов совпадают с журналом. Если работа частичная, агент использует подтверждённые результаты и повторяет только недостающее. Действие с неясным статусом и возможной платой помечает как неопределённое и сверяет перед повтором.
- **Измерения.** `run.tsv` содержит ID шага и попытки, входы и выходы, среду, модель или `unknown`, инструмент, длительность, статус, повтор и вмешательство человека. Токены и денежные затраты записываются с происхождением значения `measured`, `estimated` или `unknown`. Для оценок сохраняются метод и допущения. Отдельно видны время человека, подписка, если она нужна для запуска, и дополнительные расходы на инструменты. Неизвестная цена шага остаётся неизвестной в сводке.
- **Экономия.** По умолчанию один сеанс и одна выбранная пользователем модель. Агент открывает относящиеся к текущему вопросу файлы и фрагменты, повторно использует актуальные выписки и делает вычисления локально. Перед поиском согласует пределы по времени и количеству обращений, проверяет остаток между действиями и запрашивает решение при необходимости расширить лимит. Когда IDE скрывает расход токенов, пределы по времени и обращениям остаются проверяемыми. Использование второй модели или интеграции оценивается на том же наборе кейсов.
- **Границы доверия.** Внешние страницы и материалы кейса считаются данными. Найденные в них команды и просьбы изменить правила, раскрыть секреты, отправить файлы или открыть дополнительные сервисы игнорируются. В конкурсные материалы входят открытые источники и разрешённые собственные материалы. Секреты, закрытые данные компаний и персональные данные участников интервью исключаются. Для публичного кейса проверяются права на включение копий и происхождение каждого материала.

Воспроизводимость проверяется по сохранённым входам, версиям инструкций, ссылкам и расчётам. Для демонстрационного прогона фиксируются версия репозитория и сведения о среде. При повторе допустимы отличия в формулировках и рекомендации, если видны основания выбора и соблюдены критерии приёмки.

Первая версия ограничивается одним пишущим сеансом и ручным запуском сопровождения. Фреймворк оркестрации, хранилище эмбеддингов, сервер, субагенты, хуки и собственный MCP остаются за рамками минимальной архитектуры. Основание для расширения — повторяемое узкое место, измеренное на испытаниях.
