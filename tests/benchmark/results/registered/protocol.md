# Сравнение LLM с инструментами и агента: retention-ab-v1

Статус: подготовка, **модели не запускались**. Это один парный эксперимент на известном разработчику синтетическом кейсе. Он не измеряет переносимость на новые продукты и не является проверкой на неизвестном разработчику holdout-наборе.

## Контраст и материалы

A — обычная LLM в Codex с локальными инструментами, без проектных `AGENTS.md`, skills и workflow. Методы анализа свободны. B — та же LLM с актуальными шестью файлами инструкций агента. В обеих средах одинаковы исходный бриф, семь файлов входов, `inputs.json`, программные `tools/*.py`, `requirements.txt` и стартовый запрос. CLI доступен A, но использовать его не обязательно; B использует собственный рабочий процесс. Таким образом проверяется добавленная ценность инструкций и процедур поверх **одинакового программного оснащения**, а не модели против модели.

Программный CLI сам содержит структуры артефактов и проверки; это общий компонент, который может уменьшить различие вариантов. Его исходники не удаляются и не меняются ради A. Ограничение A касается инструкций проекта, а не самостоятельного использования доступного программного обеспечения. Не требовать от A заполнения внутренних форматов B и не начислять за них баллы.

В корне каждой копии `SOURCE_BRIEF.md` — неизменный исходный бриф, `case/brief.md` — рабочая копия. Модель может дополнять рабочий бриф, сохраняя исходный запрос. Входы, инструменты и инструкции менять нельзя; выходы и собственные расчёты сохраняются в `case/`.

## Зафиксированные условия

| Условие | Одинаково для A и B |
| --- | --- |
| Планируемая модель | `gpt-6.1-sol`, обнаружена в локальной конфигурации при подготовке |
| Thinking/reasoning effort | `medium`, обнаружен в той же конфигурации |
| Подтверждение модели | Перед обоими стартами проверить доступность и выбор в Codex; запрос, UI-метка и фактически сообщённая модель учитываются отдельно |
| Время | 30 минут wall clock от отправки START до финального ответа или принудительной остановки; ожидания, ошибки, повторы и согласования включены |
| Инструментальный бюджет | 120 фактических обращений к инструментам, включая чтение, запись, shell, polling, ошибки и повторы |
| Как считать обёртки | Каждый вложенный инструмент считается отдельно; orchestration-обёртка без отдельного действия не считается второй раз. Один shell-вызов — одно обращение независимо от числа команд, команды сохраняются в транскрипте |
| Расчёты | Одинаково разрешены Python 3.13.5/stdlib, shell и собственные скрипты; одинаковый перечень остальных доступных команд фиксируется до запуска |
| Дополнительные пакеты | Установку во время прогона не разрешать. Входы CSV/JSONL/Markdown не требуют сторонних пакетов; `requirements.txt` передан одинаково, но не означает, что все пакеты установлены |
| Внешние сведения | Ноль новых веб-запросов; только переданные локальные снимки. Web, браузер, внешние apps/MCP и поиск по другим чатам недоступны участникам |
| Архитектура выполнения | Один основной агент, без субагентов, делегирования и новых MCP; один пишущий сеанс на кейс |
| Ручная помощь | Только запуск, одинаковый контроль лимитов и фиксация. Без аналитических подсказок и исправления ответов |
| Результат | `case/strategy.md`, `case/reproduce.md`, необходимые расчёты и источниковые привязки; требования заданы общим START |

Лимиты — проектные ограничения этого эксперимента, а не результат оптимизации или подтверждённый денежный бюджет. Модельный контекст и размер ответа используют один и тот же доступный в Codex режим; если управлять параметром нельзя, отметить это, не выдумывать значение. Разница числа токенов из-за инструкций B является частью измеряемой стоимости. Никаких автоматических замен модели или effort: если план недоступен, до любого старта оформить новую версию условий **для обоих** вариантов.

Системный Python при подготовке выполняет `tools.case --help`. Его сторонние пакеты могут отличаться от проектного `.venv`; в копии `.venv` не передаётся. Для строгого прогона оператор переносит обе копии в одинаковые чистые runtime-образы и записывает версии/хеши образов. Нельзя давать одной стороне готовые аналитические скрипты, которых нет у другой.

## Копирование и проверка

Скрипт `prepare.py` читает только явный allowlist. Не копирует Git, прежние результаты, эталон, отчёты, тесты, настройки с секретами или виртуальную среду. Внешние каталоги должны быть новыми и находиться вне репозитория; перезапись запрещена. Это **рабочие копии, не git-worktree**. Пример подготовки уже использован с путями ниже:

```sh
python3 tests/benchmark/prepare.py prepare \
  --a /private/tmp/strateg-benchmark-A-20261113 \
  --b /private/tmp/strateg-benchmark-B-20261113 \
  --manifest tests/benchmark/environments.json

python3 tests/benchmark/prepare.py verify tests/benchmark/environments.json
```

Повторная подготовка требует новых путей и нового манифеста; не удаляйте принятые результаты, чтобы повторить команду. Манифест фиксирует SHA-256 и размеры **каждого** файла двух копий, соответствие оригиналам, версию инструкций по совокупности хешей и Git-коммит источника. Именно хеши файлов учитывают незакоммиченные изменения. Протокол, рубрика, промпты, скрипт и шаблоны также закреплены хешами. Их изменение после регистрации создаёт новую версию эксперимента. `registration.json` закрепляет хеш манифеста и материалов; оператор сохраняет его вне рабочих копий.

Проверка отвергает лишние файлы/каталоги, любые символические и жёсткие ссылки, общие inode и изменение файлов. Все общие файлы должны совпасть побайтно. CLI help проверяется только с `PYTHONDONTWRITEBYTECODE=1`, чтобы не загрязнять начальный снимок. После запуска используйте `verify --after-run`: рабочий бриф и новые файлы внутри `case/` разрешены, входы, исходный бриф, инструменты и инструкции остаются закреплены. Созданные Python bytecode в `tools/__pycache__/` допускаются только после запуска.

## Граница изоляции: ограничение подготовки

На этом хосте подготовлены чистые копии, **но техническая изоляция чтения не установлена**: процессы того же пользователя могут читать репозиторий и другую копию по абсолютному пути. Новый чат и отдельная папка не устраняют это. Символических ссылок в копиях нет, однако это не блокирует произвольный абсолютный путь. Текущее право `workspace-write` нельзя считать доказательством запрета чтения за пределами каталога.

Для подтверждающего запуска нужны две независимые среды ОС/VM либо сопоставимая проверенная граница чтения для **всех** доступных инструментов, включая file-read, shell, поиск и подключённые источники. В каждой среде присутствует только соответствующая копия; исходный репозиторий, эталон, `tests/evaluations/`, архив и другая среда не монтируются. Тот же путь `/workspace` внутри двух VM удобен для обезличивания. Не использовать общую домашнюю папку, git-историю, индексы поиска или историю чатов. Сохранять только необходимый доступ к сервису модели; он не даёт права получать внешние продуктовые сведения.

До START оператор без модели проверяет попытку чтения специально созданного внешнего **безвредного canary-файла** через каждый разрешённый файловый механизм: ожидается отказ. Содержание скрытых материалов не читается для этой проверки. Фиксируются команда, механизм, результат, время и политика доступа. Если механизм невозможно проверить, граница остаётся непроверенной. Самоутверждение модели «я не читал» не заменяет контроль.

Глобальные инструкции, пользовательские skills, плагины, память, автоконтекст IDE и прочие персональные настройки могут попасть в новый чат вне папки. Используйте одинаковые чистые профили; в A специализированные инструкции агента отсутствуют и не должны быть доступны даже через каталог skills. В B доступны только замороженные проектные инструкции. При подготовке глобальные `~/.codex/AGENTS.md` и `AGENTS.override.md` не обнаружены, но в текущей сессии метаданные проектных skills доступны: чистота будущих чатов **не подтверждена**.

Если такую границу обеспечить нельзя, разрешён лишь явно обозначенный **пилот с логическим разделением**: до старта отметить `read_isolation=not_established` в launch-записи. Результат нельзя называть строго слепым независимым benchmark. Не молча понижать этот статус и не трактовать отсутствие заметной утечки как доказанную изоляцию.

## Порядок ручного запуска в Codex

1. Оператор читает протокол, рубрику и `recording.md`. Прогон подготовки уже завершён; исследование ещё не начиналось. Выполнить `verify`, сохранить его результат. Не прикреплять участникам этот пакет оператора.
2. Подготовить описанную границу среды и чистые профили. В Codex добавить **сам внешний каталог A** как отдельный проект/рабочую папку (в VM — его перенос). Не выбирать исходный репозиторий и не создавать worktree из него. Создать совершенно новый чат, без fork/resume/копирования истории. Аналогично подготовить B как отдельный проект и новый чат; пока ничего не отправлять.
3. В обоих чатах вручную выбрать `gpt-6.1-sol` и `medium`, одинаковые разрешения и доступные инструменты; отключить внешний контекст и интеграции. Снять показания настроек для оператора. Убедиться, что cwd соответствует корню выбранной копии, а не `case/`. Если загрузку правил нельзя независимо проверить, отметить ограничение; не спрашивать модель об активных инструкциях перед START, так как это уже меняет экспериментальный контекст.
4. До первого старта заполнить копию `templates/launch.json`: значения модели/effort, версии приложения и runtime, инвентарь инструментов, границы чтения, путь переноса и хеши, режим пилот/подтверждающий, имя наблюдателя. Закрепить её хеш и UTC-время вне рабочих копий. Нельзя стартовать с разными моделями/effort либо незаполненными контрольными условиями. Неизвестная фактическая серверная версия допускается только как явно записанное ограничение при одинаковой запрошенной модели.
5. Для этого одиночного парного прогона порядок заранее фиксируется: **сначала A, затем B**, последовательно. Это не рандомизированный порядок; возможный эффект порядка/изменения сервиса указать в выводах. Не анализировать и не оценивать ответ A до завершения B, не переносить промежуточные результаты. В будущих повторах порядок контрбалансировать по заранее зарегистрированному плану.
6. Отправить полный текст `prompts/A.md` в чат A; запустить внешний таймер и счётчик обращений. Для B отправить полный `prompts/B.md`, начать новый таймер. Тексты побайтно одинаковы, различаются только доступные проектные инструкции.
7. Все ошибки и повторы входят в те же лимиты. За 5 минут до конца времени оператор может отправить только заранее заданное: «Осталось 5 минут исходного лимита; заверши доступный результат в установленных рамках». Одинаковое правило для обоих. На 120-м обращении либо 30-й минуте остановить активную работу средствами Codex, отменить продолжающиеся вычисления и сохранить имеющиеся файлы. Не предоставлять добавочное время на исправление. Если ответ завершён раньше, зафиксировать фактическое время.
8. Запечатать результат A до старта B по `recording.md`. Запечатать B до раскрытия контрольных материалов. Не отправлять финальный ответ одного чата другому и не продолжать исследование в этом чате подготовки. Никаких автоматически созданных чатов, запусков модели или стратегий этот пакет не выполняет.
