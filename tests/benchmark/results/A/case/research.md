# Основания рекомендации и маршрут проверки

Все численные наблюдения о «Ритме» — вычисления над синтетическими данными, не факты о реальном сервисе. R1–R13 — идентификаторы проверяемых оснований, S-xxx@1 — версии разрешённых входов. «Подтверждено» ниже означает подтверждено предоставленным документом/вычислением, не доказан причинный эффект. Ни один внешний запрос не сделан.

## R1 — структура и очистка

Выход: `calculations/qc.json`; код `analyze.py` от чтения CSV до `assert not orphan and not before`. 3 020 уникальных `user_id`, 85 080 строк сообщений, 83 738 уникальных `event_id`, 1 342 лишних доставки, максимум два сообщения на ID (проверка при первичном осмотре). Повторы идентичны по всем полям. Нет конфликтов, orphan и событий до регистрации. Проверены синтетическая метка, недельный понедельник, уникальность календаря.

Полнота до 2026-08-12 включительно; `partial` только Android 2026-07-22/23. Пропуски полей не заполнялись. Не проверены реальная точность атрибуции, разные люди за аккаунтами, семантические повторы с разными ID, фактическая платформа события или истинная серверная полнота. Повторный `task_completed` с другим ID в пределах дня не меняет бинарный исход.

## R2 — eligibility и недельные результаты

`calculations/cohorts.csv`: ключ `(cohort_week, metric)`. Поля `total`, `time_mature`, `excluded_immature`, `excluded_coverage`, `n`, `k`, `rate`; флаг `whole_week_mature` задан по воскресенью недели + конец окна. По D7 созрели недели 2026-06-01…2026-07-27; по D30 — 2026-06-01…2026-07-06. В файле также намеренно сохранены индивидуально зрелые части поздних недель: это диагностика цензурирования, не полные недельные оценки.

`eligible(u,a,b)` требует `coverage==complete` для каждого дня D[a,b] и платформы при регистрации. При отсутствии календарной даты наблюдение исключается. Исход `hit` — минимум одно событие соответствующего типа в диапазоне возрастов включительно. Отсутствие события при полном дне = 0; отсутствие полного наблюдения = неизвестно. Одно выполнение может входить в несколько разных определений метрик; они не складываются.

`calculations/user_metrics.csv`: одна строка на аккаунт; `signup_csv_line` указывает исходную строку реестра, для каждой метрики есть `_eligible` и `_hit`. Проверить события аккаунта можно прямым фильтром `events.csv` по `user_id`, затем по `event_date=signup_date+D`. Фоновая синхронизация не включена в foreground или полезное выполнение.

## R3 — основная динамика и неопределённость

`calculations/periods.csv`: периоды `early_3` = недели 1/8/15 июня; `later_3` = 22/29 июня и 6 июля; `recent_3` = 13/20/27 июля; `all_common_6`, `all_D7_9` — объединения. Все периоды задаются фиксированными списками в `analyze.py`. Основной результат: early/later для `D7_completed`, `D30_completed`, `D7_open`, `D30_open`. Числители/знаменатели: 246/776 против 245/901; 167/776 против 158/848; 357/776 против 392/901; 279/776 против 281/848. Сопоставление нескольких периодов — исследовательское, не независимые рандомизированные выборки.

`calculations/period_differences.csv`, код `additional_analysis.py`: Δ=p_later−p_early, SE=√[p_early(1−p_early)/n_early+p_later(1−p_later)/n_later], 95% Δ±1,96SE. Это нормальное приближение; не учитывает общий недельный шок и множественность сравнений. Для отдельных долей сохранён интервал Уилсона с z=1,95996398454. Наличие интервала не превращает синтетические данные в рыночное исследование.

## R4 — неполнота и границы

Для `periods.csv:later_3,D30_completed`: всего 901, полно наблюдаемы 848 (158 выполнений), 53 исключены по coverage; среди исключённых у 5 выполнение уже записано, у 48 нет. При предположении отсутствия ложноположительных отметок границы по всем 901: 163/901 и (163+48)/901. Не предполагается случайность потери; primary complete-case может иметь смещение. `coverage_lower/upper` — границы по календарно зрелым, не по незрелым. Если реальная семантика событий нарушена, даже эти границы не гарантированы.

`calculations/whole_cohort_sensitivity.csv` исключает целую неделю, если хотя бы у одного её аккаунта целевой день не `complete`. D30 для later остаются недели 29 июня и 6 июля: 108/606; early без изменений. Это иной состав периодов, не исправленный исходный эффект.

## R5 — определение возврата

`calculations/paired_window_sensitivity.csv`, `sensitivity.py`: early_2 = недели 1/8 июня, later_2 = 22/29 июня, обе группы целиком зрелы до D32. Для каждой пары точный день и окно считаются **на одном знаменателе** с полным окном. D7: 163/517 и 173/613; D6–8: 309/517 и 353/613. D30: 104/517 и 84/507; D28–32: 343/517 и 320/507. Окна качественно согласуются с направлением exact-day разности, но не доказывают регрессию продукта.

Дополнительная, менее строгая чувствительность `window_mature_sensitivity.csv` считает свои eligible N для каждого окна; её знаменатели могут различаться. Основная рекомендация цитирует парные результаты. `periods.csv` также содержит D1–7/D24–30; окно D28–32 для `later_3` имеет 45 календарно незрелых аккаунтов и не используется для основного сравнения периодов.

## R6 — состав каналов, платформ и стандартизация

`calculations/segments.csv`: ключ `(period, dimension, value, metric)`. Доли каналов для D7: `total` сегмента / `total` периода; пропуск отдельная категория. Атрибуция — последняя метка, не рандомизация. Показанные в стратегии значения organic/paid/referral взяты из `early_3/later_3`, D7. Для D30 доли в знаменателе изменяются из-за исключённых дат.

`calculations/decomposition.csv`: для `dimensions=channel`, ранние веса w0, поздние w1, доли p0/p1. `later_standardized=Σw0p1`; `within_delta=Σw0(p1−p0)`; `composition_delta=Σ(w1−w0)p1`. Их сумма ровно равна `raw_delta`. Весовая база — eligible данного исхода каждого периода, а не весь рынок. Разложение зависит от порядка/выбора весов и не оценивает причинный вклад канала. Минимальная ячейка по каналам 19; для channel+platform 5, для +stated_goal 1. Все ячейки/веса сохранены в `standardization_cells.csv`; перекрытие категорий проверяется assert. Интервал within использует независимое биномиальное приближение с фиксированными ранними весами; не учитывает оценку самих весов и неизмеренные факторы.

## R13 — сценарный размер выборки

`calculations/sample_size.csv`, `analyze.py`: для двух независимых равных групп, двухстороннего α=0,05 и 80% мощности используется нормальное приближение:

`n_per_arm=ceil((z975*sqrt(2*pbar*(1-pbar)) + z80*sqrt(p0*(1-p0)+p1*(1-p1)))**2 / (p1-p0)**2)`.

z975=1,95996398454, z80=0,84162123357, pbar=(p0+p1)/2. Нет поправки на множественные primary outcomes: основная проверка одна. В `guardrail_sample_size.csv` отдельно показана сложность исключения ухудшения раннего выполнения: n≈ceil[2p(1−p)(z95+z80)²/m²] при p=0,47, m=0,02, истинной разности 0. Это нормальное приближение для односторонней не меньшей эффективности, не оценка редких жалоб. Итоговый размер всего протокола определяется самым требовательным обязательным критерием после согласования баз и порогов. Для p0=0,20 и δ=0,05 n=1094; δ=0,03 n=2943. Для p0=0,30 и δ=0,05 n=1377. Расчёт не включает отказы в eligibility/технические потери, корреляцию аккаунтов, тесты guardrails и требования точности эффекта. Нужно пересчитать до запуска. При ровно 300 регистрациях/неделю длительность набора 2n/300; при 50% охвате — 2n/150; затем 30 дней последнего исхода и время анализа. A1–A3 — допущения для планирования, не результаты выгрузки.

## Неизвестные и гипотезы

H1/H2 из стратегии не доказаны; направление выбирается по проверяемости и продуктовой логике. A1 (ресурсы/сроки), A2 (политика сообщений, ограничения вреда/качества), A3 (эффект и экономическая иллюстрация) требуют согласования. Неизвестные из брифа сохранены: затраты разработки/привлечения, выручка, интервью, случайное назначение, историческая формула; дополнительно отсутствуют task_id/сроки, доставленные сообщения, версии клиента, кампания, реальный будущий поток и база guardrails. Автоматический подсчёт не решает эти пробелы.
